# Explicit encounter provenance and reversible initiative handoff

The encounter builder now gives canonical and homebrew anomalies explicit source identities, converts the roster into a versioned handoff plan, and embeds controlled-entity provenance in initiative combatants. New saves retain the plan for full roster/runtime restoration, while source-less legacy active state is blocked from new saves and combat sync. The initiative root contract stays unchanged by carrying workflow metadata on combatants. Two gaps block shipping: nested saved snapshots are not fully validated, and initiative JSON repeats the complete plan once per combatant.

Watch for: **confirmed** malformed restoration entries with empty IDs or non-positive quantities are accepted; **confirmed** initiative JSON grows quadratically and reaches roughly 4.5 MB with 50 instances in a representative probe; **confirmed** neither failure mode nor the tracker persistence round trip is tested.

**Verdict**: NEEDS_CHANGES

## High-level view

Canonical and homebrew records use separate identity namespaces, display names do not participate in identity, homebrew versions remain evidence, and campaign scope enters identity when roster quantities expand into controlled entities. Repeated handoffs are deterministic without conflating canonical and homebrew records that share an ID.

Save and send operations block active roster entries without explicit sources. Restoration intends to fail closed too, but **confirmed** its outer shape check and location-only validation allow malformed nested roster invariants through, restoring state the planner would refuse to build.

The initiative state retains `version`, `savedAt`, `combatants`, `currentTurn`, and `round`, and tracker hydration preserves additive combatant properties. However, **confirmed** every combatant embeds the full handoff and restoration data; because the handoff contains all expanded combatants, serialized state grows quadratically and can exceed browser storage limits.

The focused tests pass for namespaced identities, deterministic expansion, unresolved-source blocking, legacy fallback, and valid full-state restoration. **Confirmed** they do not cover adversarial restoration, payload growth, or the actual tracker hydration/persistence boundary.

## Namespaced sources become campaign-aware entity provenance

The builder assigns `canonical:<id>` or `homebrew:<id>` before selection, retains a homebrew version as evidence, and deduplicates by that namespace rather than display data. The adapter derives a stable roster entry ID, while expansion adds encounter/campaign scope and quantity index to identify each controlled occurrence.

```text
source type + source ID
          |
          v
stable roster entry + source evidence
          |
          v
encounter/campaign scope + quantity index
          |
          v
controlled entity instance + provenance
```

This separates the identity of the anomaly from the identity of one expanded combatant. The same raw ID in canonical and homebrew catalogs remains distinct, while revisions of one homebrew record keep their entity identity and retain version evidence.

## Malformed restoration snapshots bypass roster invariants

**Confirmed:** `restoreSavedEncounterWorkflowV1` uses `looksLikeHandoffPlan` to check only a few outer fields before treating persisted JSON as `EncounterHandoffPlanV1` (`src/lib/planning/adapters/encounterWorkflow.ts:413`). `buildEncounterRestorationPlanV1` validates locations but does not rerun handoff entry checks, after which the adapter copies `entry.entryId` and `entry.quantity` into builder state (`src/lib/planning/adapters/encounterWorkflow.ts:456-506`).

A runtime probe changed a valid restoration snapshot's entry ID to `""` and quantity to `0`; restoration still returned `mode: "workflow"` with those values. Initial plan construction would issue strict `encounter-entry-id-required` and `encounter-entry-quantity-invalid` blockers. A corrupted save can therefore restore duplicate/empty keys or invalid quantities, then become impossible to save or send again.

Validate the nested snapshot with the handoff planner's entry invariants: non-empty unique IDs, positive integer quantities, resolved sources, object runtime state, and required workflow metadata. A mismatch between the handoff source and restoration snapshot should block rather than trusting one copy.

## Repeated workflow envelopes make initiative JSON quadratic

**Confirmed:** every combatant stores both `handoff: plan` and `restoration: plan.restoration` (`src/lib/planning/adapters/encounterWorkflow.ts:369-375`). The handoff already includes every expanded entity and the restoration payload. Although references are shared in memory, `JSON.stringify` repeats the full graph for each combatant.

With one roster entry and a 500-character runtime description, serialized state measured about 9 KB for one instance, 239 KB for ten, 811 KB for twenty, and 4.5 MB for fifty. Real records can be larger. If serialization or local-storage quota fails, persistence logs the error, but the builder still reports success and navigates, leaving old tracker state loaded.

Keep shared workflow/restoration data under one persisted owner and put only instance identity/state plus a shared plan reference on each combatant. Preserve the existing root keys with a versioned additive envelope, and make persistence failure observable before navigation.

## Compatibility coverage stops at adapter output

Nine focused adapter/planner tests passed. **Confirmed not tested:** malformed nested IDs, duplicate IDs, invalid quantities, or inconsistent handoff/restoration snapshots. **Confirmed not tested:** serialized-size growth and local-storage failure. **Confirmed not tested:** tracker hydration, auto-roll/update, and re-persistence retaining the workflow attachment. Add adversarial restore cases, a linear-growth regression assertion for the redesigned envelope, and one tracker round-trip test.
